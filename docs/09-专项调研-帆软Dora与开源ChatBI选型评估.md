# 09 专项调研:帆软 Dora 与开源 ChatBI 方案评估

> 补充 01 文档:针对两条"不走自建"的替代路线做深入调研——**帆软 Dora(商业 Data Agent)**与**开源 ChatBI/Chatbot 方案**,并回答:**这两个方案适不适合本企业?**
> 结论先行:**均不推荐作为本项目的首选执行路线**,但各自有明确的价值定位:Dora 是商业路线下的最优候选与自建方案的"对照锚点";开源方案是 PoC 脚手架与设计参照。详见 §4 决策矩阵与 §5 重估触发条件。

---

## 1. 帆软 Dora 调研

### 1.1 产品定位与背景

| 项 | 内容 |
|---|---|
| 产品 | **Dora(朵拉)**:帆软的企业级 AI Agent / 数据智能体平台(官网 [dora.fanruan.com](https://dora.fanruan.com)) |
| 演进脉络 | FineReport/FineBI(报表与自助 BI)→ FineChatBI(问答式 BI)→ 2025 年 9 月正式发布 Dora,官方口径"ChatBI 退场,升级为 Data Agent" |
| 市场热度 | 发布后约盘出 **290 个商机、价值 5000 多万元**(内部原预估 30 个商机/约 1000 万),是当前国产 AI+BI 商业产品中热度最高者之一 |
| 核心理念 | **"AI 调用 BI,而非 AI 生成 SQL"**——复用既有 FineBI/FineReport 的指标、维度、权限资产,让 AI 在受治理的 BI 资产上执行分析,定位"原地 AI 升级" |

### 1.2 能力盘点

- **问答与取数**:自然语言查数、分析、报告与预警;底层依赖 FineBI 语义层/指标体系做意图到指标的映射(延续 FineChatBI 的"语义解析 + 指标映射"架构)。
- **多智能体/数字员工**:可搭建多个 Agent 协同,覆盖销售、财务、经营分析等场景;支持周期通报、运维稽查等自动化任务。
- **跨系统流程自动化**:可串接 ERP/BPM/协作平台,超越纯问数。
- **部署与合规**:提供**私有化 Data Agent 解决方案**(数据安全 + 业务语义 + 可信分析),支持信创环境;可接入 DeepSeek、Qwen 等国产大模型。
- **数据连接**:FineBI/FineReport **原生支持 StarRocks 数据源**(官方帮助文档提供连接配置,MySQL 协议 9030 端口),区分直连/抽取模式。
- **授权与价格**:商业授权模式,按项目/并发报价,**价格未公开**;企业生产环境需购买正式授权,另有实施与培训服务体系(如"数字员工 5 天实战打卡营")。

### 1.3 适配性评估(对照本企业 8 项关键需求)

| # | 本企业需求 | Dora 适配 | 说明 |
|---|---|---|---|
| 1 | StarRocks 3.1 数据源 | ✅ | 官方原生支持,MySQL 协议直连 |
| 2 | 单企业定制私有化部署 | ✅ | 私有化方案成熟,支持信创与国产模型 |
| 3 | 管理层小规模高可信使用 | ✅ | 产品打磨成熟,交互体验优于自研初期水平 |
| 4 | 指标口径单一事实源 | ⚠️ 部分 | 语义沉淀在 FineBI 指标体系内——**需将口径重建/迁移到帆软建模体系**,事实源从自有数仓语义层移入帆软平台 |
| 5 | 分析深度(归因/漏斗/分群/相关性) | ⚠️ 部分 | 销售/财务经营分析场景有覆盖;但本方案设计的**比率指标两段分解、恒等式拆解、跨维度贡献归因**等定制分析,受产品能力边界约束,能否实现取决于产品版本或帆软定制服务 |
| 6 | 权限与审计 | ✅ | 复用 FineBI 权限体系 |
| 7 | 定制空间(独有分析逻辑/交互/流程) | ❌ 低 | 产品化路线:边界内配置化,边界外受限;深度定制依赖厂商 |
| 8 | TCO | ⚠️ | 许可费(未公开,商务询价)+ 实施费;**上线周期短(数周级)** 是最大补偿项 |

### 1.4 结论:Dora 适不适合本企业?

**判断框架**(满足越多越适合 Dora):

1. 企业**已有 FineBI/FineReport 资产**且指标体系已在其上维护 → Dora"原地升级"价值最大;
2. 目标是**数周上线标准问数/通报**,接受产品边界;
3. 预算可覆盖商业授权,且接受口径事实源沉淀在帆软体系;
4. 无深度定制分析(归因模型、恒等式拆解、自有对话流程)诉求。

**对本企业的判定**:

- 本企业约束为"**不采用完整 BI 平台**"(见总路线),且产品目标是"AI 经营分析助手"——第 5、7 项需求(贡献归因、恒等式拆解、多轮下钻的定制分析模式)是产品差异化核心,Dora 在此处的实现深度无法验证且不可控;**与既定约束和目标冲突,Dora 不适合作为首选执行路线**。
- 但保留两个价值:**① 对照锚点**——建议在 Phase 0 向帆软询价并索取 PoC(约 1~2 周投入),用同一 Golden Set 与自建 PoC 跑对照,为立项提供性价比证据,也为谈判留筹码;**② Plan B**——若自建路线在实施中受阻(团队/工期变化),Dora 是回退选项,届时第 1 条判断框架若成立(已有帆软生态)可重估。

## 2. 开源 ChatBI/Chatbot 方案调研

### 2.1 方案盘点

| 方案 | 定位与模式 | 优势 | 劣势/风险 |
|---|---|---|---|
| **SuperSonic**(腾讯音乐,Java) | ChatBI + Headless BI 融合,语义层(schema 映射器+语义修正器)+ Text2SQL | 最接近本方案设计思想;语义层建模完善;单体 Java 服务**部署相对简单**;有腾讯音乐真实企业二次开发案例,社区活跃 | 定制个性化功能需**自行维护分支**;语义建模有学习成本;深度归因分析仍需自研 |
| **Wren AI** | 语义优先 GenBI(MDL 建模定义层),自动生成 SQL+图表+见解 | 指标治理(Governed metrics)强;多数据库兼容;多语言 | **架构重**(Wren Engine/PostgreSQL/Qdrant 多组件),私有化运维复杂;引擎为 Rust,二次开发门槛高 |
| **DB-GPT** | Agentic 数据分析开发框架(多模型/插件化) | 覆盖面广(库/Excel/数仓/知识库);插件扩展与多 Agent 编排能力强 | **开发者工具而非成品 BI**:开箱体验与可视化弱,当"问数产品"用需大量封装 |
| **Vanna AI** | RAG 式 Text2SQL 组件库(Python) | 开发灵活,易嵌入自有系统;支持自训练问答对 | **无语义层/口径治理**,长尾 SQL 准确率依赖 RAG 质量;不满足"可信分析"要求 |
| **SQLBot**(飞致云 DataEase 组,2025-08 发布) | LLM+RAG 开箱即用问数,支持 Web/弹窗嵌入与 **MCP 调用** | 极轻量,配置模型+数据源即可用;5K+ stars;可嵌入 n8n/Dify/MaxKB/DataEase;有"训练优化"机制 | 本质仍是 RAG Text2SQL 路线,**指标语义治理与深度分析能力有限**;项目较新,长期演进待观察 |
| 通用 Chatbot 平台(Dify/MaxKB/RAGFlow) | 知识库问答/Agent 编排底座 | 编排、知识库、嵌入生态成熟 | **不是问数系统**:无指标语义层、无 BI 查询与可视化语义;仅可作对话底座与 SQLBot 类工具集成 |

> 参考来源见文末;开源评测类文章的横向结论与本表基本一致:要开箱即用选 SuperSonic/Wren AI,要开发者灵活性选 DB-GPT,要轻量嵌入选 SQLBot/Vanna。

### 2.2 适配性评估(对照本企业 8 项关键需求)

| 需求 | SuperSonic | Wren AI | DB-GPT | Vanna | SQLBot |
|---|---|---|---|---|---|
| StarRocks 3.1 连接 | ✅ JDBC/MySQL 协议 | ✅ 兼容主流库 | ✅ | ✅ | ✅ MySQL 协议 |
| 私有化部署 | ✅ 简单(单体 Java) | ⚠️ 组件多、运维重 | ✅ | ✅ | ✅ 极轻 |
| 口径单一事实源(语义层) | ✅ HeadlessBI 语义层 | ✅ MDL | ⚠️ 弱 | ❌ 无 | ⚠️ RAG 级 |
| 深度归因/漏斗/分群/相关性 | ❌ 需自研 | ❌ | ❌ 需自研 | ❌ | ❌ |
| 多轮下钻/澄清体系 | ⚠️ 基础具备,深度定制需改 | ⚠️ | ⚠️ | ❌ | ⚠️ |
| 定制空间 | ✅ 高(改源码,但自担分支) | ⚠️ Rust 门槛 | ✅ 高(插件) | ✅ 高(库) | ⚠️ 中 |
| 隐性成本 | 分支维护 0.5~1 人力/年 | 多组件运维 | 封装工作量 | 自建治理层 | 治理层自补 |
| 综合 | **最接近,可参照/可 fork** | 过重 | 当框架用 | 不满足 | PoC 利器 |

**共性短板**(决定"开源拿来即用"不成立):五者均能解决"连通数据库 + 生成 SQL + 出图表",但本项目的差异化价值——**比率指标两段聚合口径、贡献归因/恒等式拆解分析模式、数字 Grounding 反幻觉、澄清与拒答策略、Golden Set 评测闭环**——全部落在"开源方案的能力边界之外",引入后仍需完成 04 文档设计的大部分自研工作。

### 2.3 结论:开源方案适不适合本企业?

- **作为生产系统直接引入:不推荐。** 要么治理深度不足(SQLBot/Vanna),要么引入不需要的重运维负担(Wren AI),要么"产品皮 + 自研芯"两头成本(SuperSonic 二次开发 + 长期分支维护,与自建轻量相比没有减少核心工作量,反而叠加了对他人代码库的理解成本)。
- **作为工程加速器:推荐,按用途取用。**
  1. **SQLBot → 2 周 PoC 脚手架**:Phase 0 用它最快验证"真实数仓 + 真实问题"下的裸 Text2SQL 准确率基线(预期显著低于语义层路线,该基线本身就是给管理层的决策证据);
  2. **SuperSonic → 设计参照**:语义层元模型、schema 映射器、语义修正器的工程实现可对照学习;其"生成逻辑卸载到语义层"的代码组织对本项目编译器设计有直接参考价值;
  3. **DB-GPT/Vanna → 不引入**,思路已在 04 文档覆盖。

## 3. 三条路线横向对比

| 维度 | A. 帆软 Dora(商业产品) | B. 开源底座(SuperSonic/SQLBot 改造) | C. 自建轻量语义层(既定路线) |
|---|---|---|---|
| 上线周期 | 数周~2 月(实施为主) | 3~4 月(改造+自研分析层) | 4.5 月(见 08 文档,含分析引擎) |
| 口径治理 | 有,但事实源在帆软体系 | 有(语义层),需学习其建模体系 | ✅ 事实源自有,口径即代码 |
| 深度分析(归因/恒等式拆解) | ⚠️ 产品边界内,不可控 | ❌ 全部自研 | ✅ 按设计实现,可复算可解释 |
| 定制空间 | 低(产品化) | 中高(受制于他人代码) | ✅ 完全可控 |
| 供应商/技术锁定 | 高(商业授权+生态) | 中(社区分支) | 低(全部自有) |
| 首年 TCO | 许可+实施(商务询价)+ 少量人力 | 0 许可 + 改造与分支维护人力 | 纯人力(6.5 人 × 4.5 月)+ 基础设施 |
| 长期演进主动权 | 跟随厂商 roadmap | 半自主 | ✅ 完全自主 |
| 适用前提 | 已有帆软生态/只求标准问数 | 团队愿承担社区分支维护 | 需要差异化分析能力/口径强治理(本企业) |

## 4. 最终建议

1. **维持既定路线 C(自建轻量语义层)执行**,理由汇总:本企业无帆软生态包袱;产品核心价值在定制分析模式(开源与商业产品边界外);单企业定制部署要求完全可控;20 人规模的自建成本可承受(08 文档预算)。
2. **Dora 处理方式**:Phase 0 商务询价 + 申请 PoC,用同一 Golden Set 做对照评测(1~2 周投入),产出物进入 M0 评审材料——既是决策证据,也是成本基准。
3. **开源方案处理方式**:SQLBot 作为 Phase 0 的裸 Text2SQL 基线工具(非生产组件);SuperSonic 列为语义层/编译器的工程参照;两者均不进入生产架构。
4. 建议在 M0 评审会上将本对比作为独立议题过审,把"为什么不用现成产品"的答案固化为组织决策,避免项目中途反复。

## 5. 重估触发条件(出现任一即重新评估)

- 工期被压缩至 **8 周以内**且分析深度要求降级为"标准问数+通报";
- 评审发现企业**已存在 FineBI/FineReport 生产资产**且指标体系愿意沉淀在帆软体系;
- 自建预算被砍半(团队 ≤3 人),且接受口径治理降级;
- Dora PoC 在自有数据上对照评测显著优于自建 PoC(执行准确率差距 >10pp 且价格可接受)。
