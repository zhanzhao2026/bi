# 01 调研报告:AI 问数技术路线、产品与模型盘点

> 目的:为"Platform-native Semantic Context + 自建轻量语义层"路线提供决策依据,明确竞品格局、准确率证据、大模型选型考量与 StarRocks 能力边界。

---

## 1. 四种技术路线对比

| 路线 | 典型形态 | 优势 | 劣势 | 对本项目适用性 |
|---|---|---|---|---|
| A. 裸 Text-to-SQL | LLM 直接读表结构生成 SQL(Vanna、DB-GPT 的基础模式) | 起步快、覆盖长尾灵活查询 | 口径漂移(同一指标多种写法)、join 易错、无法治理权限、准确率在真实企业库上明显低于基准 | ✗ 作为兜底路径保留 |
| B. BI 内嵌 Copilot | Power BI Copilot、Tableau Pulse、Quick BI 智能问数 | 可视化与报表生态成熟 | 绑定 BI 平台、语义受制于产品、定制对话分析能力弱、与管理层使用习惯不匹配 | ✗ 与"不采用完整 BI 平台"约束冲突 |
| C. Headless Semantic Layer | Cube、dbt MetricFlow、AtScale + 上层 AI | 语义治理标准化、生态完善 | 组件重、学习/运维成本高、需要长期专职维护、对小用户量团队过重 | ✗ 一期不引入(远期可评估迁移) |
| **D. 平台原生语义上下文 + 自建轻量语义层(选定)** | 语义以配置定义在本平台内,注入 LLM 上下文,输出确定性编译的 SQL | 口径单一事实源、上下文精准可控、工程量与复杂度匹配团队规模、演进自由度大 | 语义层需自建自维护;功能广度不及成熟产品 | ✓ 与约束完全一致 |

**路线 D 的本质**:把"业务知识"从 LLM 的猜测中剥离,变成平台可治理的资产(Platform-native Semantic Context);LLM 在受约束的空间内做理解与编排,计算与口径交给确定性代码。

## 2. 准确率证据(为什么语义层是必选项)

- dbt Labs 基准:裸 Text-to-SQL 64.5% vs 语义层 72.7%;**在建模良好的范围内两者都接近 100%**——说明"窄域 + 好语义建模"是企业问数的正确发力点(来源:[Atlan: Semantic Layer vs. Text-to-SQL](https://atlan.com/know/ai-agent/semantic-layer/text-to-sql-vs-semantic-layer-for-self-serve-analytics))。
- Snowflake Cortex Analyst:同一批底层模型,BIRD-SQL 上有语义模型 78% vs 无语义模型 57%。
- AtScale 研究:7 个主流模型在业务问题上,语义层平均带来 **~1.7 倍**准确率提升(来源:[AtScale press](https://www.atscale.com/press/bird-benchmark-semantic-layer-accuracy))。
- 企业级基准 BEAVER / BIRD-Ent:在 BIRD 上 ~82% 的模型迁移到真实企业库后**显著下降**——公开基准分数不能直接外推,必须以自有 Golden Set 验收(来源:[BEAVER (arXiv)](https://arxiv.org/abs/2405.19846v1))。

**结论**:管理层经营数据对错误零容忍,语义层约束不是"优化项"而是"准入条件"。

## 3. 代表产品/开源项目盘点

| 方案 | 模式 | 对本项目的启示 |
|---|---|---|
| **SuperSonic**(腾讯音乐开源) | Chat BI + Headless BI 融合:语义层封装表关联/公式,Text2SQL 生成逻辑部分从 LLM 卸载到语义层,辅以 schema 映射器与语义修正器 | 与本路线同源;**取其思想(语义卸载 + 映射修正),不引其平台**(避免整套 BI 功能包袱) |
| **Wren AI** | 语义优先 GenBI,MDL(Modeling Definition Layer)作为 LLM 可读上下文 | 印证"以建模定义语言作为 LLM 上下文载体"的可行性;我们的 YAML 规范参考其字段设计 |
| **Vanna AI** | RAG 式组件库:向量检索相似问题+DDL/SQL 对喂给 LLM | 其"历史问答对召回"可用于我们 P2 的 Few-shot 检索增强,但不解决口径治理 |
| **DB-GPT** | 自托管多模型/多 Agent 数据应用平台 | 平台过重;其数据源管理与私有模型接入思路可借鉴 |
| **Cube / dbt Semantic Layer** | 标准 Headless SL | 一期不用;语义元模型设计对齐其概念,保留远期导出/对接可能 |
| **Snowflake Cortex Analyst / Databricks Genie** | 云厂商托管语义模型问数 | 验证"语义模型 spec + 受约束生成"为企业级最佳实践;我们是自建同构物 |
| 国内商业 ChatBI(网易有数、观远、衡石等) | BI 厂商内嵌问数 | 交付形态参考:口径配置台、推荐问法、反馈纠错闭环 |
| **帆软 Dora / FineChatBI** | BI 生态 Data Agent:"AI 调用 BI 而非生成 SQL",复用 FineBI 指标与权限资产 | 2025-09 发布,市场热度高;**深入选型评估见 [09-专项调研](09-专项调研-帆软Dora与开源ChatBI选型评估.md)** |

## 4. SuperSonic 架构要点深读(最接近的参照系)

其核心闭环:`NL 问题 → Schema 映射(把口语映射到语义对象)→ 语义修正器(规则+纠错)→ 语义查询 → 解释与可视化`。三个可移植设计:

1. **生成逻辑部分卸载到语义层**:LLM 只需产出"哪个指标+哪个维度+什么时间",join/公式/过滤由语义层完成——我们把这一步形式化为"语义查询 IR + 编译器"(见 03 文档)。
2. **映射器与修正器分离**:先把口语词对齐到语义对象(同义词表),再做校验修正(枚举检查、缺失时间范围补默认)。
3. **Headless 语义层与对话层解耦**:演进时语义层可独立加固、未来可挂接其他消费端。

## 5. 大模型选型调研(2026 视角)

**需求画像**:中文电商语境理解强、结构化输出(JSON Schema/function calling)稳定、多步推理可靠、支持私有化部署选项。

| 选项类别 | 候选 | 优势 | 风险 |
|---|---|---|---|
| 云端 API(专属/私有协议) | DeepSeek-V3.x、Qwen3-Max、GLM 系列、Kimi、豆包 | 效果上限高、无 GPU 运维、按量计费 | 数据出域(需协议与脱敏)、版本漂移 |
| 私有化开源 | Qwen3-32B/72B、DeepSeek 开源系列、GLM 开源系列(vLLM/SGLang 推理) | 数据不出域、成本可控可预期 | 需 GPU 资源(如 2×A100/8×4090 量级)、推理服务运维 |
| 嵌入/轻量模型(全部本地) | BGE-M3(向量)、bge-reranker | 词义召回、离线稳定 | 无明显风险 |

**建议**:架构上做 **Model Gateway 抽象**(统一 Chat/Embed 接口、可路由、可评测);Phase 0 用同一评测集对 2~3 个候选做双轨对比(云端 API vs 私有化 Qwen3/DeepSeek 中档旗舰),以执行准确率、时延、月成本三项定案。管理层问数 QPS 极低,私有化单卡即可支撑,决策核心是**数据边界合规**而非性能。

## 6. StarRocks 3.1 能力盘点与升级评估

| 能力 | 3.1 状态 | 对本系统的影响 |
|---|---|---|
| MySQL 协议兼容 | ✓ | 任意 MySQL 驱动/连接池可用 |
| 异步物化视图 + 查询透明改写 | ✓ 基础可用 | 可为语义层补建聚合加速层 |
| 同步物化视图 / 预聚合表 | ✓ | ADS 主路径无障碍 |
| HLL / Bitmap 精确近似计数 | ✓ `hll_count`/`bitmap_count` | UV、新客数等去重指标的预聚合方案 |
| Workload Group 资源隔离 | ✓ | 为问数系统建独立资源组,限制并发/内存/扫描量 |
| External Catalog(Hive/Iceberg/JDBC) | ✓ | 一期用不上,远期跨源问数预留 |
| 3.4+ 新增(MV 透明改写增强、GROUP BY 下推等) | 需升级 | 性能锦上添花,**不构成一期前置依赖**;列为 P3 可选优化 |

**版本建议**:一期锁定 3.1 不升级(改动越少越好);在 05 文档中给出升级评估表,若后续发现 MV 改写或查询性能瓶颈再立项升级。

## 7. 关键调研结论

1. "语义层中介"是 2025-2026 年企业问数的公认最佳实践,准确率证据充分;**路线 D 确认执行**。
2. 开源产品可借鉴思想但不宜整体引入:SuperSonic/Wren 的"语义卸载 + 映射修正"模式,用约 1/10 的工程量自建轻量实现即可覆盖本项目 20 人规模的需求。
3. 企业真实库上的准确率远低于公开基准 → **必须建立自有 Golden Set 并以之为唯一验收标准**。
4. 分析类问题(归因/对比/相关性)不能靠单条 SQL:需要确定性的**分析模式库**(详见 04),这是"AI 分析助手"与"Text-to-SQL 工具"的分水岭。
5. 模型选型是可替换项,语义质量与评测体系是固定资产;架构需保证模型层可插拔。
6. StarRocks 3.1 完全满足一期需求;性能方案核心在 ADS 预聚合与资源隔离,而非版本升级。
